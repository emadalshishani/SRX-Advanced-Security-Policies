# Application-Based Security Policy Matching and Logging

## 1. Objective

This lab demonstrates application-based security policy matching on a Juniper SRX firewall. Traffic generated by a specific Ubuntu host is matched against Junos predefined applications and denied by a dedicated security policy. The enforcement is verified through local SRX session logs.

## 2. Lab environment

| Parameter | Value |
|---|---|
| Firewall | Juniper SRX – HQ |
| Source zone | `internal` |
| Destination zone | `branch` |
| Source host | Ubuntu |
| Source IP | `192.168.30.2` |
| Test destination | `8.8.8.8` |
| Address book scope | Global |

Topology images will be placed in [`images/`](images/).

## 3. Global Address Book

The Ubuntu host was defined as a Global Address Book object:

~~~bash
set security address-book global address ubuntu-user-ip 192.168.30.2/32
~~~

## 4. Security policy configuration

A dedicated policy was created from the `internal` zone to the `branch` zone. It matches the Ubuntu source address, any destination address, and DNS over UDP. The policy action is `deny`, with session-init and session-close logging enabled.

~~~bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match source-address ubuntu-user-ip
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match destination-address any
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match application junos-dns-udp
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test then deny
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test then log session-init
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test then log session-close
~~~

DNS over TCP was then added to the same policy:

~~~bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match application junos-dns-tcp
~~~

For the ICMP experiment, `junos-ping` was added temporarily:

~~~bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match application junos-ping
~~~

The ICMP application match was rolled back after the test. It is not part of the intended final DNS-filtering policy.

## 5. Experiment 1 – DNS over UDP

The first test blocked DNS over UDP while other traffic types were not explicitly added to this policy.

### Ubuntu test

The following commands were run:

~~~bash
ping 8.8.8.8
nslookup 8.8.8.8
curl -I https://google.com
~~~

Observed results:

- ICMP ping to `8.8.8.8` received replies.
- The `nslookup 8.8.8.8` attempt timed out through the Ubuntu local resolver at `127.0.0.53`.
- The initial `curl` request succeeded.

### SRX log verification

The SRX recorded DNS-over-UDP traffic as denied by the test policy:

~~~text
RT_FLOW_SESSION_DENY:
session denied 192.168.30.2/51154->8.8.8.8/53
junos-dns-udp 17(0)
internal-branch_ubuntu-user-test
Denied by policy
~~~

**Result:** The `RT_FLOW_SESSION_DENY` entry confirms that the SRX matched and denied DNS over UDP (IP protocol 17, destination port 53) using `internal-branch_ubuntu-user-test`.

**Test note:** `nslookup 8.8.8.8` is a reverse-lookup test of a numeric IP address, and the output shows the Ubuntu local stub resolver (`127.0.0.53`). It is not the clearest standalone test for a normal domain-to-IP lookup. The SRX log entry is the direct evidence that DNS-over-UDP traffic to `8.8.8.8:53` was denied. The initial successful `curl` result alone does not prove that DNS UDP was passing; a cached DNS answer may affect that test.

## 6. Experiment 2 – DNS over TCP

DNS over TCP was added to the policy with the following command:

~~~bash
set security policies from-zone internal to-zone branch policy internal-branch_ubuntu-user-test match application junos-dns-tcp
~~~

### Ubuntu test

~~~bash
curl -I https://google.com
~~~

Observed result:

~~~text
curl: (6) Could not resolve host: google.com
~~~

### SRX log verification

The SRX recorded DNS-over-TCP traffic as denied:

~~~text
RT_FLOW_SESSION_DENY:
session denied 192.168.30.2/44748->8.8.8.8/53
junos-dns-tcp 6(0)
internal-branch_ubuntu-user-test
Denied by policy
~~~

**Result:** The log confirms that DNS over TCP (IP protocol 6, destination port 53) was denied by the same security policy. With DNS UDP and TCP both matched by the deny policy, the Ubuntu host could not resolve `google.com` during the reported `curl` test.

## 7. Experiment 3 – ICMP

A continuous ping test was already running from Ubuntu to `8.8.8.8`. The `junos-ping` application was temporarily added to the policy, and the configuration was rolled back shortly afterward.

### SRX log verification

The SRX generated the following denied ICMP session entries:

~~~text
RT_FLOW_SESSION_DENY:
session denied 192.168.30.2/12->8.8.8.8/11
icmp 1(8)
internal-branch_ubuntu-user-test
Denied by policy
~~~

The `icmp 1(8)` field identifies ICMP protocol 1 and Echo Request type 8.

**Result:** The SRX logs directly confirm that ICMP Echo Request traffic from the Ubuntu host was denied by the test policy during the temporary `junos-ping` match. The ICMP match was then rolled back.

## 8. Local session-log verification

The denied-session records were inspected locally on the SRX in the `messages` log file using:

~~~bash
run show log messages | match RT_FLOW_SESSION | match udp
run show log messages | match RT_FLOW_SESSION | match tcp
run show log messages | match RT_FLOW_SESSION | match icmp
~~~

The relevant log identifier was `RT_FLOW_SESSION_DENY`. The records included the source and destination addresses, application/protocol information, the policy name, and the denial reason (`Denied by policy`).

## 9. Conclusion

This lab verified application-based security policy matching on a Juniper SRX firewall:

- A Global Address Book object was used to identify the Ubuntu source host.
- DNS over UDP was denied using `junos-dns-udp`.
- DNS over TCP was denied using `junos-dns-tcp`.
- ICMP Echo Request traffic was temporarily denied using `junos-ping`.
- Local `RT_FLOW_SESSION_DENY` logs confirmed that the intended policy denied the tested traffic.

The ICMP match was a temporary test and was rolled back. The documented DNS-filtering policy uses the UDP and TCP DNS application matches.
